# ADR-042: Generate gRPC Stubs From a Repo-Managed Protobuf Toolchain

**Status**: Accepted
**Date**: 2026-08-02
**Deciders**: project owner

---

## Context

The gRPC runtime edge (`semidx.runtime.grpc`) historically built its protobuf
messages at runtime: `semidx.runtime.grpc-proto` assembled a
`FileDescriptorProto`, called `Descriptors$FileDescriptor/buildFrom`, and
exchanged `DynamicMessage` instances, while `grpc.clj` hand-built each
`MethodDescriptor` and the `ServerServiceDefinition` with a private
`service-name "semidx.RuntimeService"`. The pinned
`proto/semidx/runtime/grpc/v1/runtime.proto` was a partial artifact: it had no
`service` block and was missing the `LiteralFileSlice` / `SnapshotDiff`
messages, so the `.proto` was documentation-only and the runtime descriptor
model was the de-facto contract (see Stage 4.4 in
`reports/014_open_gaps_closure_program_progress_log.md`).

Gap 3 of `plans/013` asks for generated Java/Kotlin stubs from the pinned
`.proto`. The forces shaping the choice:

- There is no system `protoc` and no `protoc-gen-grpc-java` on `PATH`, and we do
  not want to require one. `ADR-036` already established the project stance for
  tree-sitter: **repo-managed, pinned, no required external CLI, no silent
  fallback**. The protobuf toolchain must follow the same stance.
- `tools.deps` resolves JAR artifacts, not the platform-classified native
  executables that Google/gRPC publish for `protoc` and `protoc-gen-grpc-java`
  (classifier `exe`). Acquisition therefore needs a small dedicated
  downloader/resolver inside the build contour, not an ordinary `deps.edn` dep.
- `clojure -M:test` is a project invariant. Generating stubs must not couple the
  test run to `protoc` or to network access.

## Decision Drivers

- Reproducibility and pinning (identical bytes on every machine and in CI).
- No required external CLI at runtime or during an ordinary test run (ADR-036
  parity).
- `.proto` as the single editable source of truth; no drift between the wire
  contract and the runtime.
- Preserve the runtime envelope messages and the error-trailer taxonomy
  (`x-sci-error-code` / `x-sci-error-category`, correlation trailers).
- Keep `clojure -M:test` working out of the box after a clean clone.

## Considered Options

### Option 1. Repo-managed pinned toolchain + committed generated Java

Acquire pinned `protoc` and `protoc-gen-grpc-java` executables as build-only
artifacts, generate Java stubs from the `.proto`, commit the generated sources,
and javac-compile them to `target/classes`. `protoc` runs only when the `.proto`
changes or when verifying generated drift.

### Option 2. Generate into `target/` on every build, commit nothing

No generated sources in the tree. Every test/CI run must run codegen first.

### Option 3. Keep the runtime `DynamicMessage` builder; only sync the `.proto`

Do not adopt generated stubs; make the `.proto` complete and add a test that the
descriptor model matches it.

## Decision

We accept Option 1: a repo-managed, pinned, build-only protobuf toolchain with
committed generated Java and idempotent javac preparation.

The pipeline has four independent stages:

```
download pinned tools  ->  .proto -> generated Java  ->  javac -> target/classes  ->  Clojure runtime/tests
```

Concretely:

1. **Pinned toolchain (build-only).**
   - `protoc` **3.25.1** and `protoc-gen-grpc-java` **1.63.0**. This is the pair
     recommended by the grpc-java 1.63.0 README and matches the project's
     `io.grpc/*` 1.63.0 and `com.google.protobuf/protobuf-java-util` 3.25.1
     dependencies.
   - Executables are the Maven-published platform-classified `exe` artifacts,
     fetched over HTTPS from Maven Central, SHA-256 verified, and cached under
     `.cache/semidx/protobuf/` (git-ignored). They are **not** ordinary
     `deps.edn` dependencies and are never on the runtime classpath.
   - Pinned SHA-256 (extend the table as platforms are validated):

     | tool | version | classifier | sha256 |
     |------|---------|------------|--------|
     | protoc | 3.25.1 | osx-aarch_64 | `b6ed65c0d20a9ab88ec6995644f747d557cb9a087eab0152fef5367c34645dc3` |
     | protoc-gen-grpc-java | 1.63.0 | osx-aarch_64 | `28290117a2ee9ea60f50f94273ab139dc2b3be4b8f2a557bef7e6efefee5b363` |
     | protoc | 3.25.1 | linux-x86_64 | `936e423041c6977036208366507964d5615782b5a450ec8d3d52ff557ffc7101` |
     | protoc-gen-grpc-java | 1.63.0 | linux-x86_64 | `0e3e8db80ba1fbddeed97ea3220b52cfaa95764ff8bf00716df7322883ce47e8` |

   - A platform is supported only after both artifact hashes have been validated
     and added to the pinned table. The validated classifiers are
     `osx-aarch_64` and glibc-based `linux-x86_64`. Candidate classifiers for
     later validation are `osx-x86_64`, `linux-aarch_64`, and
     `windows-x86_64`.
     Missing or unsupported classifiers raise an explicit build error rather
     than silently falling back to a system `protoc`.
   - grpc-java 1.63.0 publishes the `osx-aarch_64` plugin artifact as a
     byte-identical copy of its `osx-x86_64` Mach-O binary. Apple Silicon
     codegen therefore requires Rosetta 2 even though classifier selection still
     resolves `osx-aarch_64`. The resolver validates the pinned checksum and an
     execution probe; it does not reject the upstream artifact merely because
     its Mach-O architecture differs from the classifier name.

2. **`.proto` is the single editable source of truth.** It now carries the full
   contract: `java_multiple_files`, `java_package`, the previously missing
   `LiteralFileSlice` / `SnapshotDiff` messages, and a `RuntimeService` service
   block with all eight unary methods. The service is versioned under the proto
   package, so the full gRPC service name becomes
   `semidx.runtime.grpc.v1.RuntimeService`. This is an intentional change from
   the pre-versioned `semidx.RuntimeService`: no `service` block previously
   existed in the `.proto`, so there was no committed wire service contract.
   The RPC **method** names (`Health`, `CreateIndex`, ...) are unchanged, but the
   full wire paths change from `/semidx.RuntimeService/<Method>` to
   `/semidx.runtime.grpc.v1.RuntimeService/<Method>`.

3. **Committed generated Java, git-ignored build outputs.** Generated sources
   are committed under `src-generated/java`. `target/classes`, `*.class`, and any
   generated JAR are git-ignored. Effect: an ordinary build or test run needs no
   `protoc` and no network — only the committed sources and a javac step.

4. **`:build` alias (tools.build).** Build tasks:
   - `grpc-generate` — acquire the toolchain and regenerate `src-generated/java`.
   - `grpc-verify-generated` — regenerate into a temp directory and diff against
     the committed sources; non-empty diff fails (deterministic drift guard).
   - `compile-java` — javac `src-generated/java` -> `target/classes`.
   The generated grpc-java service class references `@javax.annotation.Generated`
   (JSR-250, absent from JDK 17), so `javax.annotation:javax.annotation-api:1.3.2`
   is added as a small compile/runtime dependency.

5. **Idempotent javac keeps `clojure -M:test` working.** The `:test` and
   `:runtime-grpc` aliases put `target/classes` on the classpath and run an
   idempotent `ensure-grpc-classes!` before the JVM loads the gRPC namespaces:
   if the compiled classes are missing or older than the committed Java sources,
   it runs **javac only** (never `protoc`); otherwise it does nothing. After a
   clean clone the first run compiles once; subsequent runs are no-ops.

6. **Descriptor parity precedes cutover.** The pre-existing `DynamicMessage`
   builder was used once as a parity oracle across all 16 messages, then
   removed. The runtime now uses the generated `RuntimeServiceGrpc`
   method/service descriptors and generated message classes; the error-trailer
   taxonomy and correlation trailers are unchanged.

Option 2 loses because it makes `protoc` and network access a hard dependency of
every test/CI run, creating hidden developer-machine state and local/CI
divergence — the exact anti-pattern ADR-036 rejects. Option 3 loses because it
does not deliver generated stubs (the stated Gap 3 goal) and keeps a bespoke
runtime descriptor assembler as the contract.

## Consequences

### Positive

- The `.proto` becomes the enforced single source of truth; `grpc-verify-generated`
  fails on drift.
- No protobuf toolchain download or `protoc` invocation is needed for ordinary
  builds, tests, or a clean-clone run; only a one-time javac after dependency
  resolution.
- Message and service types come from standard generated stubs instead of a
  hand-rolled runtime descriptor assembler, aligning with the grpc-java ecosystem.
- Toolchain acquisition is pinned and SHA-256 verified, matching the ADR-036
  reproducibility bar.

### Negative

- Generated Java sources are committed, adding reviewable but machine-authored
  files under `src-generated/java`.
- A `:build` contour (tools.build), a small downloader/resolver, and an
  idempotent javac prep step are new build surface to maintain.
- Adds `javax.annotation-api` as a small dependency for compilation.
- The full gRPC service name changes to the versioned
  `semidx.runtime.grpc.v1.RuntimeService`; any external client hard-coding the
  old `semidx.RuntimeService` must update its full method paths. The in-repo
  tests reuse shared method descriptors and migrate with the runtime cutover.

### Follow-Up

- The prebuilt `protoc-gen-grpc-java` for Linux depends on glibc; musl/Alpine is
  **not** a silently supported platform. It must either raise the explicit
  unsupported-platform error or be handled by a separate, explicitly validated
  artifact before Alpine is claimed as supported.
- `linux-x86_64` is validated for the glibc-based GitHub Actions runner. Other
  classifiers remain unsupported until both executable hashes are validated and
  pinned.
- Apple Silicon codegen depends on Rosetta 2 because the grpc-java 1.63.0
  `osx-aarch_64` plugin artifact is actually an x86_64 Mach-O binary. This does
  not affect ordinary tests or runtime after generated sources are committed.

## Definition Of Done

`proto/.../runtime.proto` is complete and authoritative; `src-generated/java`
holds committed stubs regenerated only via `clojure -T:build grpc-generate`;
`grpc-verify-generated` passes with no drift; `clojure -M:test` and
`clojure -M:runtime-grpc` work from a clean clone with no system `protoc`;
`semidx.runtime.grpc` uses the generated stubs with the error-trailer taxonomy
unchanged; and the runtime `DynamicMessage` builder has been removed.
