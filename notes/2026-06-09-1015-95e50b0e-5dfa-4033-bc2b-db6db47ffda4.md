# План работ: расширение `semidx`

## Назначение

Это опорный концепт для последующего планирования изменений в `semidx`.

Документ фиксирует:

- проверенное состояние текущей реализации;
- архитектурные решения, которые не следует пересматривать без новых данных;
- реальные пробелы относительно желаемого развития;
- рекомендуемую последовательность работ;
- границы будущих исполнимых планов.

Эта заметка является текущей концептуальной точкой опоры. Конкретные
implementation-планы для отдельных этапов должны создаваться в `plans/` и
ссылаться на неё.

## Исходные Материалы

В основу концепта положены:

- архивный план [006_semidx_improvement_plan.md](../ideas/006_semidx_improvement_plan.md);
- архивная исследовательская записка
  [semidx: лучшие практики Serena и IntelliJ](../ideas/007_semidx_serena_intellij_best_practices.md);
- предыдущая заметка
  [Persistent Index and Incremental Reuse](2026-03-27-persistent-index-incremental-reuse.md);
- анализ текущего исходного кода и тестов `semidx` от 2026-06-09.

Исходные документы сохранены как исторический контекст, но больше не являются
активным планом или источником истины.

## Главный Вывод

Направление исходных предложений верное: `semidx` следует развивать как единый
семантический слой над кодом, документацией, контрактами, тестами и
зависимостями, используя разные источники анализа.

При этом значительная часть предлагаемой архитектурной основы уже существует.
Нельзя начинать работу с повторного создания нормализованной модели, снимков,
fallback-механизма или базовой инкрементальности.

Ближайшая задача состоит в том, чтобы:

1. гарантировать актуальность повторно используемого индекса;
2. отделить обнаружение файлов от списка поддерживаемых языков;
3. расширить текущую Semantic IR типизированными отношениями;
4. доказать архитектуру на Markdown и YAML;
5. только затем подключать новые языковые и внешние semantic providers.

## Проверенное Состояние Реализации

### Нормализованная Semantic IR Уже Есть

Текущая реализация уже нормализует результаты разных парсеров через
`semidx.runtime.semantic-ir`.

Подтверждено наличие:

- единого результата парсинга файла;
- нормализованных units;
- `parser_mode`;
- diagnostics;
- `semantic_pipeline`;
- стабильного `semantic_id`;
- `semantic_fingerprint`;
- `public_shape_fingerprint`.

Опорные файлы:

- `src/semidx/runtime/semantic_ir.clj`;
- `src/semidx/runtime/semantic_id.clj`.

Решение:

- не вводить параллельную модель `IndexedDocument` как второй источник истины;
- расширять существующую Semantic IR;
- сохранять обратную совместимость текущих units, calls и imports.

### Снимки И Хранилище Уже Есть

Текущая реализация уже поддерживает:

- `snapshot_id`;
- сохранение и загрузку индексов;
- загрузку последнего и закреплённого снимка;
- in-memory и Postgres storage;
- идентификацию репозитория, workspace, ветки и commit;
- provenance снимка;
- parent snapshot;
- `snapshot_diff`.

Опорные файлы:

- `src/semidx/runtime/index.clj`;
- `src/semidx/runtime/storage.clj`;
- `src/semidx/runtime/repo_identity.clj`;
- `src/semidx/runtime/snapshot_diff.clj`.

Решение:

- не планировать persistent snapshots с нуля;
- развивать существующий storage contract;
- считать shared indexes продолжением текущего storage и repo identity, а не
  отдельной новой подсистемой.

### Базовая Инкрементальность Уже Есть

`update-index` уже:

- принимает `changed_paths`;
- удаляет старые units и diagnostics изменённых файлов;
- повторно парсит только переданные пути;
- объединяет результат с неизменившейся частью индекса;
- создаёт новый снимок с provenance `incremental_update`.

Ограничение:

- вызывающая сторона должна заранее знать `changed_paths`;
- после слияния глобально перестраиваются производные индексы;
- нет автоматического определения добавленных, изменённых и удалённых файлов;
- нет точечной инвалидации типизированных отношений.

### Fallback Уже Есть, Но Недоступен Для Неизвестных Форматов

`adapters/parse-file` умеет деградировать до fallback-unit при ошибке парсера
или неподдерживаемом языке.

Однако неизвестные текстовые форматы обычно не доходят до этого слоя:

- `source-files` принимает только пути, распознанные `source-path?`;
- `source-path?` зависит от фиксированного списка языковых расширений;
- `create-index` выдаёт `no_supported_languages_found`, если поддерживаемый язык
  не обнаружен.

Следствие:

- YAML, Markdown и неизвестные текстовые файлы отбрасываются до индексирования;
- основная проблема находится в discovery и activation, а не в отсутствии
  fallback как такового.

### Capability, Confidence И Guardrails Частично Реализованы

Текущая retrieval-система уже сообщает:

- `parser_modes`;
- `coverage_level`;
- `fallback_unit_count`;
- силу поддержки выбранных языков;
- `confidence_ceiling`;
- provenance индекса;
- evidence, confidence и guardrails результата.

Опорные файлы:

- `src/semidx/runtime/retrieval_policy.clj`;
- `src/semidx/runtime/retrieval.clj`;
- `src/semidx/runtime/semantic_quality.clj`.

Ограничение:

- capability пока выражается преимущественно через силу языка и parser mode;
- нет явного negotiation по операциям `definitions`, `references`,
  `implementations`, `call_hierarchy`, `diagnostics` и другим возможностям
  провайдера.

### Project Context Не Является Полной Моделью Проекта

`semidx.runtime.project-context` управляет:

- каноническим root;
- tenant scope;
- registry индексов;
- состояниями активации языков;
- конкурентным refresh.

Он пока не моделирует:

- modules;
- source roots;
- test roots;
- generated roots;
- SDK;
- внешние библиотеки;
- dependency scopes.

Решение:

- не считать текущий project context аналогом IntelliJ project model;
- будущую project model строить отдельно, сохраняя текущий registry lifecycle.

### Публичный MCP Surface Уже Ориентирован На Агентов

Существующие MCP-инструменты:

- `create_index`;
- `repo_map`;
- `resolve_context`;
- `expand_context`;
- `fetch_context_detail`;
- `literal_file_slice`;
- `snapshot_diff`;
- `impact_analysis`;
- `skeletons`.

`resolve_context` уже принимает структурные targets и ограничения по путям,
модулям, тестам и языкам.

Отдельных `find_symbol`, `find_references` и `find_implementations` пока нет.
Добавлять их следует только после появления общей модели типизированных
отношений и ясного пользовательского выигрыша.

## Главные Проблемы

### P0. MCP Cache Может Вернуть Устаревший Индекс

Ключ MCP-кэша учитывает root, paths, parser options и language policy, но не
учитывает текущее состояние файлов.

Повторный `create_index` способен вернуть `cache_hit` после изменения
репозитория, если ключ запроса не изменился.

Это дефект корректности. Он должен быть устранён до расширения покрытия
документов и языков.

### P0. Загруженный Persisted Snapshot Не Проверяется По Содержимому

`load_latest` умеет загружать сохранённый снимок и проверять его возраст, но не
проверяет соответствие текущему содержимому рабочей копии.

Необходимы:

- fingerprint состояния индексируемых файлов;
- автоматическое определение добавленных, изменённых и удалённых путей;
- явные причины reuse, incremental update и rebuild.

### P1. Discovery Жёстко Связан С Поддерживаемыми Языками

Сейчас обнаружение файлов, определение языка и решение об индексируемости
фактически объединены.

Необходимо разделить:

```text
Repository Discovery
→ Text/Binary And Safety Classification
→ Format Detection
→ Provider Selection
→ Semantic IR
```

Репозиторий должен считаться индексируемым, если найден хотя бы один безопасный
файл, для которого доступен structured или fallback provider.

### P1. Нет Общей Модели Типизированных Отношений

Текущая модель хорошо поддерживает calls, imports, callers, callees, module
dependents и test targets.

Для документов и бизнес-контрактов необходимы отношения вида:

```text
Reference {
  source_unit_id
  target_key
  relation_type
  resolution_status
  confidence
  provenance
  evidence_location
}
```

Примеры `relation_type`:

- `calls`;
- `imports`;
- `defines`;
- `references`;
- `implements`;
- `extends`;
- `links_to`;
- `trigger_event`;
- `source_state`;
- `target_state`;
- `test_targets`.

Calls и imports должны остаться совместимыми проекциями общей модели, а не быть
немедленно удалены.

### P2. Нет Единого Provider Contract

Добавление языка сейчас требует изменений в нескольких фиксированных местах:

- список поддерживаемых языков;
- extension detection;
- dispatch в `adapters/parse-file`;
- parser options;
- тесты с литеральным списком языков.

Нужен один расширяемый provider contract. Не следует одновременно вводить
дублирующие абстракции `FormatIndexer` и `SemanticProvider`.

Рекомендуемая модель:

```text
SemanticProvider {
  id
  detect(file_metadata)
  capabilities
  index(file_content, context)
}
```

Провайдеры могут быть:

- native parser;
- tree-sitter;
- LSP;
- JetBrains;
- structured document;
- text fallback.

## Архитектурные Решения

### Позиционирование

`semidx` не должен становиться IDE или самостоятельно реализовывать
компилятор-grade анализ каждого языка.

Целевая роль:

> единый межъязыковой семантический граф с компактным agent-oriented retrieval,
> объединяющий код, документы, контракты, тесты и зависимости.

### Единственный Нормализованный Контракт

Все провайдеры должны передавать данные в расширенную текущую Semantic IR.

Недопустимо:

- создавать отдельный document graph, не связанный с units;
- заставлять orchestrator знать правила YAML, Markdown или конкретного языка;
- смешивать точные и эвристические отношения без provenance и confidence.

### Качество Должно Быть Наблюдаемым

Каждый результат должен позволять определить:

- какой provider создал факт;
- какой parser mode использован;
- какая capability доступна;
- является ли отношение точным, структурным, convention-based или текстовым;
- насколько свежий снимок использован;
- является ли результат полным или degraded.

### Embeddings Не Являются Доказательством Связи

Embeddings допустимы только как дополнительный механизм поиска кандидатов и
ранжирования. Они не должны создавать точные semantic relationships.

### AutoParts Policies Не Должны Попадать В Общий YAML Provider

YAML provider должен создавать общую структуру документа.

Предметные правила AutoParts должны подключаться отдельной настраиваемой
reference policy.

## Последовательность Работ

### Этап 0. Корректность Повторного Использования Индекса

Цель:

- гарантировать, что `create_index` не возвращает устаревший индекс.

Работы:

- определить fingerprint индексируемого состояния;
- хранить fingerprint и необходимые file metadata в снимке;
- обнаруживать добавленные, изменённые и удалённые файлы;
- проверять MCP cache hit перед возвратом;
- автоматически вызывать существующий `update-index`;
- добавить явные lifecycle outcomes:
  - `no_changes`;
  - `incremental_update`;
  - `full_rebuild`;
  - `storage_reuse`;
  - `cache_recovered_after_corruption`;
- определить порог перехода от incremental update к full rebuild.

Первый исполнимый план должен охватывать только этот этап.

Минимальный acceptance:

1. Изменение файла между двумя одинаковыми вызовами `create_index` не возвращает
   устаревший snapshot.
2. Неизменившийся репозиторий не запускает парсеры повторно.
3. Добавление и удаление файлов корректно отражаются в новом snapshot.
4. Инкрементально обновлённый индекс семантически эквивалентен полному rebuild.

### Этап 1. Разделение Discovery, Format Detection И Activation

Цель:

- разрешить индексирование репозиториев без поддерживаемых языков.

Работы:

- обнаруживать безопасные потенциально индексируемые файлы независимо от языка;
- добавить text/binary detection;
- добавить ограничения размера;
- отделить `language_id`, `format_id`, `provider_id` и `support_level`;
- сохранить существующую language activation как политику активации code
  providers;
- разрешить structured-only и fallback-only индекс;
- возвращать coverage summary по файлам и форматам.

Минимальный acceptance:

1. Репозиторий только с Markdown создаёт индекс.
2. Репозиторий только с неизвестным безопасным текстом создаёт fallback-only
   индекс.
3. Двоичные, слишком большие и исключённые файлы не индексируются.
4. Причина исключения каждого файла наблюдаема.

### Этап 2. Расширение Semantic IR Типизированными Отношениями

Цель:

- создать общую основу для кода, документов и контрактов.

Работы:

- добавить relation/reference model;
- добавить provenance, confidence и resolution status;
- построить forward и reverse relation indexes;
- сохранить calls/imports как совместимые проекции;
- расширить `impact_analysis`, `snapshot_diff` и capability summary.

Минимальный acceptance:

1. Существующие caller/callee тесты остаются зелёными.
2. Типизированное отношение можно добавить без изменения orchestrator.
3. Unresolved и ambiguous отношения представлены явно.
4. Impact analysis умеет обходить новые отношения.

### Этап 3. Markdown Vertical Slice

Цель:

- доказать structured-document indexing на простом формате.

Первая версия:

- document;
- heading sections и их иерархия;
- links и anchors;
- fenced code blocks;
- tables и list blocks как неделимые фрагменты;
- секция как базовая единица retrieval.

Минимальный acceptance:

1. `repo_map` показывает документные области.
2. `resolve_context` возвращает конкретную секцию, а не весь файл.
3. Относительные ссылки создают типизированные отношения.
4. Markdown-only репозиторий индексируется без ручного выбора языка.

### Этап 4. YAML Vertical Slice

Цель:

- индексировать структурированные бизнес-контракты.

Первая версия:

- document;
- top-level definitions;
- named mappings;
- sequence items с устойчивыми именами;
- fields, enums, enum values;
- workflows, steps, states и transitions;
- duplicate-key diagnostics;
- подключаемая reference policy.

Минимальный acceptance для AutoParts:

1. `location_assigned` связывает enum, transition, workflow и fixture.
2. Удаление enum value переводит отношения в unresolved.
3. Добавление определения разрешает ранее unresolved отношение.
4. AutoParts-specific conventions отсутствуют в общем YAML provider.

### Этап 5. Точечная Инвалидация Отношений

Цель:

- не перестраивать весь граф при локальном изменении.

Работы:

- использовать reverse relation index;
- вычислять изменённые semantic keys;
- повторно разрешать только затронутые отношения;
- повторно проверять потенциально изменившиеся unresolved и ambiguous
  отношения;
- публиковать новый snapshot атомарно.

### Этап 6. Provider Contract И Capability Negotiation

Цель:

- упростить подключение новых языков и внешних анализаторов.

Работы:

- ввести registry провайдеров;
- убрать фиксированный dispatch из центрального адаптера;
- описать capabilities каждого provider;
- выбирать лучший доступный provider;
- явно сообщать degraded capability;
- сохранить bounded fallback.

### Этап 7. Kotlin И Gradle Kotlin DSL

Начинать после стабилизации provider contract и typed relations.

Рекомендуемый порядок:

1. Kotlin structural provider через tree-sitter или LSP.
2. Базовые declarations, calls, inheritance и implementations.
3. Отдельное определение Gradle Kotlin DSL.
4. Module dependency relations.
5. Android-specific классификация только после базовой корректности.

Не писать собственный глубокий Kotlin semantic analyzer без доказанной
необходимости.

### Этап 8. Project Model

Добавить нормализованные:

- modules;
- source roots;
- test roots;
- generated roots;
- dependencies;
- external libraries.

Project model должна дополнять текущий project registry, а не заменять его.

### Этап 9. Swift И Дополнительные Форматы

После Kotlin и project model:

- Swift через SourceKit-LSP, SwiftSyntax или другой provider;
- SQL;
- JSON;
- XML;
- TOML;
- `.properties`;
- Shell.

Каждый формат должен добавляться отдельным ограниченным изменением.

### Этап 10. Внешние Providers И Гибридный Retrieval

После стабилизации локального provider contract:

- LSP providers;
- JetBrains provider;
- shared index artifacts;
- lexical retrieval;
- embeddings как дополнительное ранжирование.

## Что Не Следует Делать

- Не начинать с JetBrains или LSP интеграции.
- Не вводить новую Semantic IR параллельно существующей.
- Не строить plugin framework раньше первого работающего provider registry.
- Не добавлять Kotlin, Swift, YAML и Markdown одним изменением.
- Не считать текущий MCP cache корректным только потому, что он возвращает
  `cache_hit`.
- Не использовать возраст snapshot как единственный критерий свежести.
- Не представлять документные отношения только как calls.
- Не скрывать fallback-only или degraded результаты.
- Не включать AutoParts conventions в общий YAML parser.
- Не использовать embeddings вместо точных отношений.
- Не превращать `semidx` в редактор или IDE.

## Риски

### Устаревший Индекс

Наивысший риск: агент принимает устаревший cache hit за актуальный индекс.

Митигация:

- fingerprint состояния;
- автоматическое change detection;
- тесты на изменение, добавление и удаление файлов;
- семантическая эквивалентность incremental update и full rebuild.

### Параллельные Модели

Риск: document indexing создаёт отдельную модель, несовместимую с текущими
units и retrieval.

Митигация:

- расширять Semantic IR;
- ввести один provider contract;
- сохранить совместимые проекции.

### Ложная Семантика

Риск: convention-based и fallback отношения выглядят как точные.

Митигация:

- provenance;
- confidence;
- resolution status;
- capability ceiling;
- явная degraded диагностика.

### Преждевременная Универсализация

Риск: provider framework становится самостоятельным проектом до появления
Markdown/YAML результата.

Митигация:

- сначала минимальный contract;
- затем Markdown vertical slice;
- затем YAML vertical slice;
- обобщать только подтверждённое повторение.

### Нарушение Обратной Совместимости

Риск: typed relations ломают существующие calls/imports и retrieval.

Митигация:

- additive model;
- совместимые проекции;
- существующие regression и onboarding tests остаются обязательным gate.

## Границы Первого Исполнимого Плана

Следующий отдельный артефакт в `plans/` должен описывать только этап 0:
корректность повторного использования индекса.

Он должен определить:

- модель file-state fingerprint;
- источник истины для Git и non-Git репозиториев;
- поведение с dirty worktree и untracked files;
- обработку удалённых файлов;
- cache-key и lifecycle semantics;
- границу между reuse, incremental update и full rebuild;
- атомарность публикации снимка;
- тестовую матрицу;
- последовательность небольших изменений и коммитов.

Discovery, Markdown, YAML и provider registry не должны входить в тот же первый
implementation plan.

## Трасса Проверки

### Проверка 1. Discovery И Unsupported Formats

- **Проверено:** `src/semidx/runtime/language_activation.clj`,
  `src/semidx/runtime/adapters.clj`.
- **Наблюдение:** discovery принимает только пути с известным языком;
  Markdown-only репозиторий вызывает `no_supported_languages_found`.
- **Вывод:** structured и fallback formats блокируются до parser dispatch.

### Проверка 2. Semantic IR И Stable Identity

- **Проверено:** `src/semidx/runtime/semantic_ir.clj`,
  `src/semidx/runtime/semantic_id.clj`.
- **Наблюдение:** нормализация, stable semantic identity и fingerprints уже
  реализованы.
- **Вывод:** новую параллельную нормализованную модель вводить не нужно.

### Проверка 3. Snapshot И Storage

- **Проверено:** `src/semidx/runtime/index.clj`,
  `src/semidx/runtime/storage.clj`, `src/semidx/runtime/repo_identity.clj`.
- **Наблюдение:** persistent snapshots, pinned/latest load, Postgres storage и
  repository identity уже существуют.
- **Вывод:** требуется freshness validation и change detection, а не новая
  storage foundation.

### Проверка 4. Incremental Update

- **Проверено:** `semidx.runtime.index/update-index` и связанные runtime tests.
- **Наблюдение:** изменённые пути парсятся отдельно, но должны быть переданы
  вызывающей стороной; производные индексы перестраиваются глобально.
- **Вывод:** автоматическое change detection является первым практическим
  пробелом.

### Проверка 5. MCP Cache

- **Проверено:** `semidx.mcp.core/tool-create-index` и MCP server tests.
- **Наблюдение:** cache hit определяется по параметрам запроса, а не по
  состоянию файлов.
- **Вывод:** cache correctness имеет приоритет P0.

### Проверка 6. Retrieval Capabilities

- **Проверено:** `src/semidx/runtime/retrieval.clj`,
  `src/semidx/runtime/retrieval_policy.clj`,
  `src/semidx/runtime/semantic_quality.clj`.
- **Наблюдение:** confidence, evidence, guardrails и capability ceiling уже
  существуют; operation-level provider capabilities отсутствуют.
- **Вывод:** capability negotiation следует расширять поверх текущей модели.

### Проверка 7. Project Context И MCP Surface

- **Проверено:** `src/semidx/runtime/project_context.clj`,
  `src/semidx/mcp/core.clj`, `src/semidx/contracts/schemas.clj`.
- **Наблюдение:** project context управляет lifecycle индекса, но не моделирует
  структуру проекта; MCP surface уже agent-oriented.
- **Вывод:** project model и дополнительные symbol tools являются отдельными
  последующими задачами.

Создать в `plans/` отдельный исполнимый план этапа 0: устранение устаревших
cache hits и автоматическое инкрементальное обновление индекса.
